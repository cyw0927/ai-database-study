## 4. 핵심 활동: 잘못된 SQL의 의미 추적하기

다음 데이터를 사용합니다.

| 학생 | 질문 수 |
| --- | ---: |
| 학생 A | 2 |
| 학생 B | 1 |
| 학생 C | 0 |

AI가 다음 SQL을 작성했습니다.

```sql
SELECT COUNT(*) AS student_count
FROM students AS s
INNER JOIN questions AS q
    ON q.student_id = s.id;
```

| --- | --- |

| 학생 A는 몇 행으로 나타나는가? |  |
| `COUNT(*)`는 실제로 무엇을 세는가? |  |

## 12. 권장 해설

### 저장 방식 선택

```text
저장 방식에는 하나의 절대적인 정답이 없다.
현재 데이터 양뿐 아니라 관계, 동시 작업, 반복 조회,
정확성, 권한, 이력과 복구 요구사항을 함께 본다.
```

- 개인 독서 기록은 파일이나 스프레드시트로 시작할 수 있습니다.
- 단기 행사 명단은 스프레드시트가 편리하지만 반복 운영과 개인정보 권한이 중요해지면 DBMS를 검토합니다.
- 온라인 강의 신청은 학생·강의·신청의 관계와 상태가 중요하므로 관계형 DBMS가 적합합니다.
- 주문·결제·재고는 동시에 처리되는 작업과 실패 복구가 중요하므로 트랜잭션이 필요합니다.

### 전체 학생 수와 학생별 질문 수

```text
전체 학생 수
→ students 행 수

학생별 질문 수
→ 학생을 기준으로 질문을 연결하고 학생별로 집계
```

`INNER JOIN`은 질문이 없는 학생을 제외하고, 1:N 관계에서는 학생을 여러 행으로 반복시킬 수 있습니다. 결과 숫자가 예상과 같아도 실제로 무엇을 셌는지 확인해야 합니다.

### `NULL`과 0

```text
NULL → 값이 없거나 미입력·미확정
0    → 값이 확정되었고 그 값이 0
```

업무에서 같은 의미라고 확인된 경우에만 변환합니다.

### 기준 데이터와 파생 결과

```text
기준 데이터
→ 업무 판단의 근거

파생 데이터
→ 기준 데이터를 계산해 만든 결과

AI 생성 결과
→ 모델·입력 데이터·지시에 따라 달라질 수 있는 결과
```

### 신청 금액과 실제 결제

```text
신청 당시 저장한 금액
≠ 실제 결제·환불 기록
```

실제 결제를 관리하려면 결제 상태와 별도의 기록이 필요합니다.

### 스프레드시트에서 DBMS로 전환해야 하는 신호

```text
같은 정보가 여러 행에서 반복된다.
동시 수정 충돌이 자주 발생한다.
업무 상태와 관계 규칙을 수동으로 확인한다.
반복 조회·집계가 점점 복잡해진다.
권한·감사·복구 요구사항이 커진다.
웹이나 앱이 같은 데이터를 지속적으로 사용한다.
```
