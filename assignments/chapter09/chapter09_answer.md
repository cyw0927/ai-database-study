# 4. 첫 번째 정상 COMMIT 추적

실행 파일: `code/chapter09/03_commit_transaction.sql`

학생 101이 강의 301을 신청한다. 저장소 SQL을 읽어 보면 강의 301 좌석을 하나 차감하고, 그 결과가 만들어졌을 때에만 신청과 결제 행을 이어 만든다.

## 4-1. 하나의 업무 단위

```text
1) 강의 301 잔여 좌석을 1 감소한다.
2) 학생 101의 실습 신청 9001을 생성한다.
3) 신청 금액과 같은 결제 9901을 생성한다.
```

셋 중 하나만 반영되면 좌석은 줄었는데 신청은 없거나, 신청은 있는데 결제가 없는 식으로 업무 상태가 어색해진다. 그래서 세 변경을 한 트랜잭션으로 묶고 최종 검증을 통과한 경우에만 COMMIT한다.

## 4-2. 상태 변화표

아래 값은 제공된 SQL의 사전 조건과 검증 조건을 기준으로 한 **예상값**이다. 실제로 실행하지 않았으므로 실측으로 표시하지 않는다.

| 시점 | 강의 301 남은 좌석 | 신청 9001 | 결제 9901 | 상태 |
| --- | ---: | --- | --- | --- |
| BEGIN 전 | 2 | 없음 | 없음 | seed 기준 예상 |
| 트랜잭션 내부 | 1 | student 101 / course 301 / 100,000 | 9001에 연결 / 100,000 | 아직 COMMIT 전 |
| COMMIT 후 | 1 | 존재 | 존재 | 검증 성공 시 확정 |

![설명용 도식: 좌석 확보와 신청·결제의 원자적 흐름](./images/step04_commit.svg)

*그림 2. 세 변경의 관계를 설명하는 도식이며 실행 결과 캡처가 아니다.*

## 4-3. 영향 행 수와 COMMIT 판단

좌석 차감은 `remaining_seats > 0`인 행만 업데이트한다. `WITH seat AS (UPDATE ... RETURNING ...)`의 결과를 다음 INSERT들의 입력으로 쓰기 때문에 좌석 확보가 0행이면 신청과 결제도 따라 만들어지지 않는 구조다. 기대 좌석 UPDATE는 1행, 기대 신청과 결제도 각 1행이다.

| 확인 내용 | 기대 | 실측 |
| --- | ---: | --- |
| 좌석 UPDATE | 1행 | 미실행 |
| 신청 INSERT | 1행 | 미실행 |
| 결제 INSERT | 1행 | 미실행 |
| 신청 금액과 결제 금액 | 100,000으로 일치 | 미실행 |
| 통과 메시지 | `Chapter 09 first commit validation passed` | 미실행 |

SQL 문장이 오류 없이 끝났다는 것만으로 업무가 맞다고 할 수는 없다. 조건이 너무 넓어서 엉뚱한 행을 바꾸거나, 예상보다 많은 행을 바꾸는 문장도 문법적으로는 정상일 수 있다. 그래서 “실행 성공”과 “기대 행 수”와 “최종 관계가 맞음”을 따로 봐야 한다고 이해했다. 처음에는 `RETURNING`이 그냥 화면에 결과를 보여 주는 기능인 줄 알았는데, 다음 CTE에서 성공한 행만 이어 쓰는 데도 쓸 수 있다는 점이 유용했다.

# 5. ROLLBACK으로 임시 변경 취소

실행 파일: `code/chapter09/04_rollback_transaction.sql`

이 파일은 강의 302의 임시 신청을 트랜잭션 안에서 만든 뒤 ROLLBACK한다. 이후 확인할 기대 상태는 좌석 302가 다시 1이고 신청 9002와 결제 9902가 없는 것이다. 앞 단계에서 이미 COMMIT한 9001/9901과 강의 301의 좌석 1은 그대로여야 한다.

| ROLLBACK 후 확인 | 기대값 | 실측 |
| --- | --- | --- |
| 강의 302 남은 좌석 | 1 | 미실행 |
| 신청 9002 | 없음 | 미실행 |
| 결제 9902 | 없음 | 미실행 |
| 이전 COMMIT 9001/9901 | 유지 | 미실행 |
| 기대 메시지 | `Chapter 09 rollback validation passed` | 미실행 |

여기서 제가 궁금했던 것은 “ROLLBACK이면 바로 전 단계까지 통째로 되돌아가나?”였다. 답은 현재 열려 있는 트랜잭션에 한정된다. 이미 COMMIT된 9001은 이번 트랜잭션의 변경이 아니므로 취소 대상이 아니다.

## IDENTITY 값은 왜 되돌아오지 않을 수 있나

일반적인 PostgreSQL 시퀀스 번호 할당은 트랜잭션 롤백과 같은 방식으로 취소되지 않는다. 이번 스크립트는 ID를 직접 지정하고, 두 번째 파일에서 그 ID를 다시 쓸 수 있도록 시퀀스도 별도로 맞춘다. 자동 번호가 중간에 빠져도 각 행의 고유 식별 목적은 유지된다. 번호가 모든 업무에서 빈틈없는 순번이어야 한다면 IDENTITY를 회계 번호처럼 취급하지 말고 별도의 순번 정책을 설계해야 한다.

# 6. 두 번째 COMMIT과 좌석 부족

실행 파일: `code/chapter09/05_commit_and_sold_out.sql`

첫 부분은 학생 103이 강의 302를 신청한다. 저장소의 seed 기준에서 강의 302는 좌석 1개이므로 정상 신청 후 0이 되는 것이 기대된다.

```text
예상 신청: 9002 / student 103 / course 302 / recorded_amount 120000
예상 결제: 9902 / enrollment 9002 / amount 120000
예상 강의 302 잔여 좌석: 0
```

두 번째 시도에서는 남은 좌석이 0이라 조건부 UPDATE가 0행을 돌려준다. 이는 SQL 문법 오류가 아니라 현재 조건에서는 바꿀 행이 없다는 결과다. 다만 업무적으로는 신청을 받아들이지 못한 상태이므로 성공으로 간주하면 안 된다. 이 스크립트는 좌석 UPDATE 결과를 CTE로 연결해서 9003/9903이 생기지 않는지 확인하고, 이 시도 자체는 ROLLBACK한다.

| 확인 내용 | 기대값 | 실측 |
| --- | ---: | --- |
| 매진 상태 좌석 UPDATE | 0행 | 미실행 |
| 신청 9003 | 생성 안 됨 | 미실행 |
| 결제 9903 | 생성 안 됨 | 미실행 |
| 최종 메시지 | `Chapter 09 sold-out validation passed` | 미실행 |

좌석 UPDATE가 0행인데 뒤에서 무조건 INSERT를 실행했다면 좌석을 확보하지 못했는데 신청과 결제만 생기는 모순이 생길 수 있다. 이 SQL에서는 `seat` CTE가 비어 있을 때 다음 CTE의 INSERT 입력도 비어 있으므로 0행으로 이어진다. 이 부분을 읽으면서 “0행이면 예외를 던져야만 실패인가?”라고 생각했는데, 반드시 예외만이 답은 아니고 결과를 업무 실패로 판정해 후속 변경을 막는 설계도 가능하다는 점을 보았다.

# 8. 이번 실습으로 이해한 ACID

| 속성 | 이번 예시로 설명 |
| --- | --- |
| Atomicity | 좌석 차감, 신청 생성, 결제 기록이 같이 성공하거나 같이 취소된다. |
| Consistency | 트랜잭션 전후 좌석 범위, 신청-결제 금액, 활성 신청 수와 사용 좌석 같은 규칙이 맞아야 한다. |
| Isolation | 두 세션이 같은 마지막 좌석을 동시에 바꾸려 할 때 잠금과 조건부 UPDATE가 경쟁을 조정한다. |
| Durability | COMMIT된 신청 9001 같은 결과는 성공 응답 후 확정된 데이터로 남는다. |

Atomicity와 Consistency가 같은 말은 아니다. 트랜잭션은 여러 변경을 한 덩어리로 성공/취소시키지만, 업무 규칙이 잘못 작성되어도 그 잘못된 변경들을 한꺼번에 COMMIT할 수 있다. 그래서 제약조건, 조건부 변경, 기대 영향 행 수, 여러 테이블 검증이 함께 필요하다.

# 9. 선택 실습 — 두 세션 Lock 관찰

실행 파일: `code/chapter09/07_concurrency_two_sessions.sql`

**수행 방식: 절차 분석만 기록.** 이 환경에서 서로 다른 PostgreSQL 세션 두 개를 열어 대기/timeout을 직접 확인하지 못했다. 따라서 아래는 스크립트의 의도에 대한 분석이며 관찰 결과로 주장하지 않는다.

| 순서 | Session A | Session B | 예상 관찰 |
| ---: | --- | --- | --- |
| 1 | BEGIN 후 강의 303 행을 `FOR UPDATE`로 잠금 | 아직 실행 전 | A가 해당 행 잠금을 보유 |
| 2 | 트랜잭션을 열린 채 유지 | 같은 행 잠금 요청 | A가 끝나지 않았다면 B가 대기할 수 있음 |
| 3 | COMMIT 또는 ROLLBACK | 대기 중 | A의 잠금 해제 |
| 4 | 종료 | 잠금 요청 계속/timeout 처리 | B가 진행하거나 `lock_timeout`이면 오류 |

Lock 대기는 한 쪽의 잠금이 해제되길 기다리는 상태다. Deadlock은 서로 상대가 가진 잠금을 기다리는 순환 상태다. 한 세션이 다른 세션을 기다렸다는 사실만으로 Deadlock이라고 부를 수 없다.

`SELECT ... FOR UPDATE`는 행을 잠근 뒤 그 값을 바탕으로 여러 판단을 해야 할 때 유용하다. 반면 조건을 포함한 UPDATE 자체가 원자적으로 행을 변경하고 `RETURNING`/영향 행 수로 성공 여부를 확인할 수 있다면, 앞서 별도 SELECT 잠금이 항상 필요한 것은 아니다. 필요한 동시성 정책을 먼저 생각하고 잠금을 선택해야겠다.

# 10. 선택 실습 — 취소와 좌석 복구

실행 파일: `code/chapter09/08_cancel_and_restore.sql`

이 스크립트는 신청 9001의 상태를 수강중에서 취소로 바꾸고, 실제 취소에 성공한 행만 입력으로 삼아 강의 301 좌석을 복구한다. 같은 취소를 한 번 더 시도하면 이미 상태가 바뀌었으므로 업데이트는 0행이고 좌석 복구도 0행이어야 한다. 맨 마지막에는 ROLLBACK하여 주 실습 상태를 보존하도록 되어 있다.

| 항목 | 기대 | 실제 |
| --- | --- | --- |
| 첫 취소 UPDATE | 1행 | 미실행 |
| 강의 301 좌석 변화 | 1 → 2 | 미실행 |
| 같은 취소 재시도 | 0행 | 미실행 |
| 두 번째 좌석 복구 | 0행 | 미실행 |
| 전체 ROLLBACK 후 | 신청 9001 수강중, 좌석 1 | 미실행 |
| 통과 메시지 | `Chapter 09 cancel rollback validation passed` | 미실행 |

취소를 두 번 받아 좌석을 두 번 늘리면 남은 좌석이 실제 정원보다 커질 수 있다. 이 SQL은 성공한 상태 변경의 `RETURNING` 결과만 좌석 복구에 연결해서 같은 요청이 다시 와도 좌석이 한 번만 복구되게 한다. 결제 행은 이번 범위에서 실제 환불을 모델링하지 않기 때문에 남긴다고 README와 SQL 주석이 알려 준다. 취소와 환불은 현실에서는 같은 사건이 아니구나 싶었다.

# 11. 선택 실습 — 오류 상태와 SAVEPOINT

실행 파일: `code/chapter09/09_error_and_savepoint.sql`

이 파일은 오류를 내는 SQL이 주석 처리되어 있어 기본 실행만으로 오류를 경험하는 것은 아니다. 안내대로 주석을 해제하고 실행할 때는 중복 활성 신청을 시도해 고유 인덱스 위반을 만들 수 있다. PostgreSQL은 트랜잭션 안에서 오류가 나면 현재 트랜잭션이 실패 상태가 될 수 있다. 오류 전에 SAVEPOINT를 만들었다면 `ROLLBACK TO SAVEPOINT`로 해당 지점 뒤의 변경만 되돌리고 트랜잭션을 이어갈 수 있다.

```text
예상: SAVEPOINT 이전 좌석 차감은 복구 대상이 됨
예상: 중복 신청 9003은 생성되지 않음
예상: 전체 실습 마지막 ROLLBACK으로 기준 상태 보존
실행 및 실제 오류 문구: 미확인
```

SAVEPOINT는 오류를 무시하는 주문이 아니다. 어느 변경까지 되돌린 뒤에도 업무가 여전히 말이 되는지 설계해야 한다. 어떤 예외든 무조건 살려서 계속하면 더 이상 올바르지 않은 상태를 만들 수 있다.

# 14. 최종 성찰

```text
1. 트랜잭션은 여러 SQL을 단순히 묶는 것이 아니라
   한 업무의 변경을 함께 성공 또는 실패시키고, 검증 결과에 따라 확정하는 경계이다.

2. ROLLBACK이 필요한 대표 상황은
   좌석 확보 조건이 맞지 않거나, 후속 변경/최종 검증이 실패한 때이다.

3. 조건부 UPDATE의 영향 행 수가 중요한 이유는
   문장은 성공했어도 조건을 만족하는 행이 없어 업무 변경은 실패했을 수 있기 때문이다.

4. 제약조건이 있어도 트랜잭션이 필요한 이유는
   여러 테이블의 변경이 하나의 업무이므로 일부만 남는 상황을 막아야 하기 때문이다.

5. Lock이 필요한 이유는
   동시에 같은 좌석을 변경하는 작업이 서로의 판단을 무효화하지 않게 조정하기 위해서이다.

6. AI가 만든 트랜잭션 SQL을 검토할 때 가장 먼저 확인할 것은
   업무 경계, 실제 스키마, 영향 행 수, COMMIT 전 정합성 검증이다.
```

## 한 문장 요약

> 트랜잭션은 관련된 업무 변경을 한 성공·실패 경계 안에 두고, 영향 행 수와 최종 정합성이 확인됐을 때만 COMMIT하는 방법이다.
